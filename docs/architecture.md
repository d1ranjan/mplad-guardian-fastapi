# MPLAD Guardian Architecture

MPLAD Guardian is an evidence-first audit-intelligence application. It prioritises public-project records for analyst review and does not label people, vendors, or institutions as fraudulent. Each alert must preserve a reproducible analysis run, source records, detector evidence, component score, review status, and reviewer note.

## Domain model

The primary unit is a **project**. Every project is linked to one vendor and can include financial milestones. An import record preserves the uploaded CSV metadata and storage reference. An audit run records the execution timestamp, algorithm version, source snapshot digest, and count of reviewed projects. Alerts are generated by a specific run; evidence records retain the human-readable measurements supporting each finding. Reviewer actions are immutable event records rather than overwritten history.

## Explainable detector policy

| Detector | Reviewable signal | Primary evidence |
|---|---|---|
| Cost outlier | Cost versus comparable category, district, and financial-year peers | Actual and sanctioned value, peer median, deviation, peer count |
| Duplicate work | Normalised title/description similarity plus locality, date, and coordinate proximity | Similarity percentage, matching locality, distance, dates, linked project |
| Vendor concentration | Vendor project/value share and Herfindahl–Hirschman concentration in a locality-period cohort | Vendor share, concentration value, cohort count, linked project list |
| Stalled project | Overdue expected completion plus incomplete progress, spend, and stale update | Days overdue, progress, expenditure ratio, days since update |
| Data quality | Missing, inconsistent, malformed, or implausible source fields | Field name, source value, validation condition |

## Score policy

Scores are bounded from 0–100. A project may have multiple independent alerts, each retaining its detector score. The dashboard priority score is the maximum open alert score for the project, not a claim of probability or wrongdoing. Risk bands are: critical (80–100), high (60–79), moderate (35–59), and low (0–34).

## Reviewer workflow

Analysts can filter, inspect, and update alerts. Available actions are **mark for field verification**, **dismiss with a note**, and **resolve with a note**. Every action records the actor, action type, timestamp, and note. The case view displays project source data, peer context, linked projects, score breakdown, evidence, and reviewer history.

## Import workflow

The import screen previews a CSV locally, checks headers and field-level rules, presents blocking errors and non-blocking warnings, then sends validated records to the typed API. The original file is stored in object storage and its key, filename, checksum, row count, and validation summary are retained in the import record.

## Demo data policy

The seed dataset is explicitly synthetic and documented. It contains safe fictional project and vendor names. The reliable demonstration cases are: `MPL-OD-105` for peer-cost deviation, `MPL-MH-202` paired with `MPL-MH-201` for potential duplicate work, `MPL-AS-301` for vendor concentration, `MPL-RJ-401` for a stalled project, and `MPL-OD-106` for a completion-status versus progress data-quality exception. These examples enable a reliable demo without suggesting wrongdoing by real individuals or organisations.
